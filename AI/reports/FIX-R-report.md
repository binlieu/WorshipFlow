# FIX-R report: which FIX-Q changes measure better (interleaved A/B)

Feature IDs UI (Show, Cues, Media), SYS. Brief `AI/specs/FIX-R-keep-what-measures-better.md`. Level: **Implemented, Unit Tested** (unchanged code), measured in the running app (Release measuring build, replayed gestures and drops, this Mac, **the screen was locked for every run**). Not Hardware Verified, not Live-Service Verified. No migration. **No product code changed in this task: every unit that was measured is kept** (decisions below; one of them, unit b, is a judgement call that is flagged for the owner).

## Method

- **Units** (from `git show d6594de`): (a) the Release compile and hook-string check in `scripts/check.sh` (and `scripts/package-test-build.sh`); (b) `TickingWhile` for the Media controller row, the Media mode's audio cue card and the sound rows (KI-190): `WFControls.swift`, `MediaDockView.swift`, `MediaAudioColumn.swift`, `AudioPanel.swift`; (c) grid cells reading their own marks: `ObservedShow.swift` (`isSelected(at:)`, `isLive(at:)`, the per-position observation notes), `SlideGridCell.swift`, `CentrePane.swift` (`ScrollToSelection`, the grid no longer reads selection, live place or mode), tests `FIXQ_MarksTests`, `FIXQ_ViewSourceTests` (grid and cell parts); (d) the Cues slide-action list working out the chosen slide once and being a `LazyVStack`: `CuesEditors.swift`; (e) the `#if DEBUG || WF_MEASURE` hooks, `PhaseProbe`, `UISnapshotFixQ`, `MainThreadMeter`, `scripts/fixq-run.sh`, `lib-measure-build.sh`; (f) anything else: **nothing**. The other 40-odd files of the commit change only `#if DEBUG` to `#if DEBUG || WF_MEASURE`, and the `PhaseProbe.time` wrappers in `AppModel.swift` (no-ops in the packaged app, a few microseconds in the measuring build, the same in every variant).
- **Variants**, each a Release build with `WF_MEASURE`, same derived-data folder, built from one scratch copy of the tree at HEAD with the unit's files put back to their `1d1e3be` text: `full` (HEAD), `noB`, `noC`, `noD`, and `base` (b, c and d all put back: the product code of `1d1e3be` with the FIX-Q measuring hooks; the literal `1d1e3be` has no hooks, so this is the closest thing that can be measured the same way).
- **Interleaving**: 3 rounds, each round visits all five variants once, each visit = `fixq-run` equivalent (12 runs per gesture, all six modes) then the drop replay (`UISnapshotFixM`), 200 slides, 100 bin items, a temporary library, `--silent-audio`. Order per round: full noB noC noD base / base noD noC noB full / noC full base noB noD. Then, because the first batch left two questions open, a second batch: full, a scratch build with a 16 ms-per-100 ms background spinner, and noB (3 rounds, gestures only), and four more rounds of full against noC (drops only). Scratch folders deleted afterwards.
- **Numbers** below are the median over rounds of each round's median, with [min to max over rounds]. The **noise floor** is that spread for the same variant. Measured: bursts of gestures 0.5 to 2 ms (Next full 15.1 to 16.8); total CPU 1 to 3 ms; **drops 5 to 10 ms and more**, each run is one drop, and the two batches an hour apart differed by up to 2x for the same variant (reorder, noC: 24 to 30 ms in batch 1, 45 to 58 in batch 2; dock, full: 15.8 then 4.5). A gap smaller than that spread is "no measurable difference".
- `burst` = the longest uninterrupted run of main-thread CPU in one run-loop pass (the metric of the 8 ms target). `CPU` = main-thread CPU in the call and the 0.7 s after (1.5 s for drops), not reduced by idle unless said. `stall` = 2 ms heartbeat gap, includes waits (a locked screen makes it 16 at rest).

## The one open decision: unit (b), kept on a judgement

The brief's rule keeps a unit that is better on some gesture and not measurably worse on any, and says not to roll back a measured benefit. (b) is both: a very large measured benefit (idle CPU 30 times lower; the whole window 3 to 4 times less main-thread CPU around a command) and a measured **burst** that is longer on Show gestures. I kept it because:

1. The work per command is the same in both: the same view bodies run (checked in the phase lines of every run: Next runs `MediaClearButtons`, `PreviewMonitor`, two or three `SlideGridCell`, one `SlideThumbnail`, `TransportBar` in every variant). Only how long the same bodies take differs.
2. A control: with `full` plus a background thread that burns 16 ms of every 100 ms (about the load the tick put on the main thread, but nothing to do with the window), the Next burst fell from 16.2 [15.1 to 16.8] to 12.5 [11.4 to 15.1], Go Live from 11.5 to 9.0, Previous from 14.8 to 11.5, and CPU from 36.5 to 26.8. So a large part (about 60% for Next) of what the tick "buys" in the burst metric is the machine being busy and warm (clock and core state), not less work. It is **not all** of it: Clear (29.4 plain, 29.1 spinning, 20.1 with the tick), Blackout and Go Live after Clear did not move with the spinner, so some of the effect is real and its cause is not known.
3. Idle CPU at 16% of a core all day is also a cost (heat and power on a Mac that may be a fanless laptop or a small box at the back of the hall), and the burst of Next with the tick (10 ms) still misses the 8 ms target, without it (16 ms) misses by more.

This is a judgement against the rule's letter on one metric. **If the owner prefers the faster burst to the idle CPU, rolling back (b) is a clean revert of four files** (`WFControls.swift`: delete `TickingWhile`; `MediaDockView.swift`, `MediaAudioColumn.swift`, `AudioPanel.swift`: put back the three `TimelineView(.periodic(from: .now, by: 0.1))`; and remove the test `theMediaControllerRowTheCueCardAndTheSoundRowsTickOnlyWhileSomethingPlays` in `FIXQ_ViewSourceTests`); the `noB` build measured here is exactly that tree. KI-190 would be reopened.

## Is there a slowdown against `1d1e3be`?

Interleaved: yes in the burst metric for Show gestures, by 1.0 to 1.4 times (Next 12.9 to 16.6, Previous 12.3 to 14.0, Go Live 9.3 to 11.5, Clear 21.2 to 27.4, Go Live after Clear 23.2 to 30.8; Blackout, Edit, Stage, Screens equal), and the cause is established to a good part: the removed 10 Hz tick (KI-190), whose absence leaves the main thread idle between commands (see the spinner control). It is not (c) or (d): `noC` and `noD` match `full`, and `noB` is faster than `base` while `base` differs from it only in (c) and (d). Against the wall-clock stall (what the heartbeat sees, includes waits) there is no slowdown: full is equal or better than `base` on Previous (13.1 against 15.3), Next by key 16.1 against 17.9, Blackout 16.5 against 19.3 and 20.8, Clear 26.1 against 31.1. The CPU a command costs fell by 3 to 4 times. So FIX-Q's report was right that "no gesture measurably got faster", wrong to read the longer bursts as an unexplained slowdown (KI-191 updated), and the drops' "longer bursts" (reorder 24 to 38) are mostly the same effect plus a large run-to-run noise.

## Not verified, stopped short of

- The screen was locked for every run (`CGSSessionScreenIsLocked` true in all 15 runs of the first batch that log it; the second batch does not log it, same session), so a display commit waits for a frame; nothing was clicked by hand. Hand-felt difference between the variants is unknown; an unlocked-screen run was not made.
- The literal commit `1d1e3be` was not measured (no hooks); `base` is its product code with the hooks. Differences: the measuring scripts and tooling files, which do not run in a gesture.
- Three rounds per variant (12 runs per gesture per round) is a small sample for the drops, where each run is one drop and the batch-to-batch drift is large; I read a drop difference as real only where it held in every round. Only the unit (c) drops were repeated (7 rounds).
- The cause of the "busy thread runs the same work faster" effect (clock, core, caches, SwiftUI's own caches) is unknown; the spinner shows a generic part, not all of it.
- Gesture speed in a Debug build, MIDI (unaffected by these units), hardware: not measured.
