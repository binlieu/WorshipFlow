# FIX-E report: fixes from the independent review of CUE-002b

Features: CUE-002b, CUE-003, CUE-004. Verification: Implemented; Unit Tested; Simulated (fake server, fake MIDI ports, a token store whose writes fail) and real loopback sockets for the remote tests. Not Hardware Verified, not Live-Service Verified. No migration was needed.

## Method and one deviation

Test-first was NOT followed in the strict sense: I wrote the code for items 1, 2, 3, 5, 6, 7 and 9 and then the tests (a process slip), instead of seeing each test fail first. To make up for it I copied the changed package to a scratch folder, reverted each behaviour there (no cancelling in Clear/Blackout, no refusal gate, no flush after a revoke, no serialisation, macro endpoint ignoring problems, addresses looked up on every refresh, no missed-event list) and ran the new tests: each group failed in the right place (for example `blackoutOnCancelsTheWaitingStepAndBlackoutStaysOn` saw the second Next run; `aRevokeIsOnDiskByTheTimeItReturns` saw the old row; the switch tests saw two servers). The scratch copy was removed from the repository tree's concern (it lives in the session scratch folder). No git state was changed.

## Items

1. **Failed revoke (high): done.** `LibraryTokenStore` now writes through a `RemoteTokenPersistence` seam (the library by default), retries a failed pairing or revoke write (3 attempts), and `flush()` returns the problem in words (`nil` when all is saved). `revokeDevice` and `revokeAllDevices` return only after the write; on failure the operator gets a notice and an activity line ("... is not saved ... may be able to connect again after WORSHIPFLOW restarts. Revoke it again."). The in-memory cache refuses the token at once in every case. A pairing whose write fails is reported when it happens; `stopRemote` and `flushRemote` report problems too. Tests (`FIXE_RevokeTests`, 7): failed revoke and revoke all are told and still refused (401); a write that fails once is retried silently; a revoke is on disk when it returns (deletes are made slow so a missing wait would show); a revoked token is still refused after the server is switched off and on; failed pairing reported; the store returns a problem once from `flush()`. Touch (lastUsed) failures are retried but not reported (no loss).
2. **Cancel waited steps (high): done.** Blackout on (and a toggle that turns it on), Clear, Clear all and Stop, from any source and also inside another macro, drop every waited step of every running macro or schedule run; the macro that does the cancelling keeps its own later steps (so `[Blackout on, wait, Blackout off]` still works). Activity line "cancelled: N waiting step(s)" (N counts actions). Blackout off cancels nothing. The engine got `cancelWaiting(except:)`, a count readout, a defaulted `blackoutWillTurnOn()` on `CueTarget` (default false, so existing fakes are unchanged) and an opt-in `cancelsWaitingStepsOnClear` (default false) that the app's `CueModel` turns on: the existing engine test `blackoutClearAndOtherMovesDoNotCancelPendingStages` pins the engine's own rule that those moves do not cancel, a first full check failed on it, and I kept that test and made the new rule opt-in instead of editing it. Tests (`FIXE_CancelWaitingTests`): the brief's scenario for Blackout from four sources, toggle, Clear, Clear all, Stop, Blackout off, a macro's own steps, another macro's Clear.
3. **Remote on/off interleaving (medium): done.** Start, stop and port change are queued on one chain (`remoteChain`); the setting saved at the end of each step is what is actually listening. The server sits behind a `RemoteServing` protocol (the real `RemoteServer` conforms) with an injectable factory. Tests (`FIXE_RemoteSwitchTests`, with a fake whose `start` suspends): on then on starts one server; on then off during the start ends with nothing listening and the setting off (saved too); a port change during a start ends listening on the new port only.
4. **KI-087 order: no change**, pinned by `aNextThatCrossesIntoAnotherItemRunsAfterTheMacrosOtherSteps` (log `clear`, then `next begin`, `next end`).
5. **Hardware Test (medium): done.** While it runs, `submit` and `run` refuse commands from MIDI, remote and schedule; the refusal is an activity line (no notice per press); `run` returns the reason so the phone gets 409 with it. Buttons and keys unaffected. Tests (`FIXE_HardwareTestTests`): each source at model level, buttons and keys still work, a MIDI note through fake ports, the remote over loopback (409 with "Hardware Test", then 200 after the test ends).
6. **Event due during the test (small): done.** Notice kept; also `missedEvents` (new, with `dismissMissedEvents()`), which also takes the skipped events; the schedule view shows them under "Not run" with Dismiss all. Tests: listed during the test, still listed after it ends, dismissed; a skipped event is listed too. The view itself was not looked at in a running app.
7. **Remote macro endpoint (low): done.** `CueRemoteTarget.runMacro` throws `rejected` with the first problem, so the endpoint answers 409 like transport. Test with a macro whose step names a missing Look.
8. Covered by item 1.
9. **getifaddrs on the tick (low): done.** The addresses are computed when the server starts and by `networkChanged()`, which an `NWPathMonitor` calls (started only when the server runs, not on a loopback-only run, cancelled on stop). `refreshRemote()` uses the cache; nothing runs when the server is off. Test counts calls to `localAddresses`: 1 after start, still 1 after ten refreshes, 2 after a network change, 2 after stop. The monitor itself was not exercised (no real network change).
10. **Wake observer (low): done** in `AppModel.shutdown()` (App target; no test possible, one small change).
11. **Wall-clock sleep (low): done.** `CueModel.reloadSettled()` awaits the reload that a re-flow starts; `CUE002b_SlideActionsTests` line 111 now awaits it instead of sleeping 200 ms (that one line only; assertions unchanged).
12. **MIDI debounce: no change;** recorded as KI-089.
