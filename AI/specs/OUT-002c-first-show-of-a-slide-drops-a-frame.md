# OUT-002c: the first time a slide is shown, the output drops one frame

Feature IDs: OUT-002, KI-007 (render and output path). Model: Sonnet. One agent in the main folder; nothing else is in flight. No migration. This is in the live output path: one small, explained change, tests first.

## Evidence

A 10-minute soak on a 60 Hz display, never covered (`AI/reports/soak-screen2-600s-20261123-0750.log`, not in git; OUT-002b's per-event list): 35,989 frames presented, 7 dropped, every one a single missed refresh (33.33 ms), at 0.234, 5.234, 10.350, 15.450, 20.533, 25.650 s and one at 531.733 s. The soak advances a slide about every 5.1 s (117 advances in 600 s). So the first six drops fall on the first six slide advances, and the later 111 advances drop nothing: the cost is paid the first time each distinct slide is drawn (the soak cycles a small set of slides; confirm how many). The earlier 60-minute run at 100 Hz had 75 drops, consistent with the same cause plus others.

## What to do

1. **Confirm the cause before changing anything.** Read the soak's slide set (`App/Sources/SoakConfig.swift` and what it calls) and the path from a new scene to a drawn frame (`OutputRenderer`, `Compositor`, the text and image caches). Find what is done for the first time on the render or presentation path when a scene with unseen content arrives: Core Text layout and glyph rasterisation, texture allocation and upload, image decode, pipeline state creation, a cache miss that takes a lock. Measure it with a test that renders an unseen scene and then the same scene again and records the work each did (count of cache misses, textures created: counts, never wall-clock assertions). State the cause with that evidence. Also say what could explain the single drop at 531.7 s (cache eviction or size limit, the video loop point, a system event) and whether the evidence supports any of them; do not guess as fact.
2. **Fix it so a new scene costs the render thread no first-use work,** by the smallest change that fits the existing design. The expected shape, to confirm: when a scene is published, its textures are prepared off the render thread (the existing text cache and image cache filled on a background queue, bounded, cancellable when a newer scene arrives) and the renderer keeps presenting the previous scene until the new one's resources are ready, then switches in one frame; the wait is bounded (if preparation takes longer than a stated limit, about 3 frames, it switches anyway and draws as today, so a command is never held back visibly and never lost). Go Live, Next, Blackout and Clear must still reach the screen in order; Blackout and Clear need no preparation and must never wait. A second option to weigh: prepare the Next slide's resources when the current one goes live (it is known in the show state), so that the usual advance is already warm; say which you chose and why, or do both if each is small.
3. **Tests first** (write, see fail for the right reason, then implement; do not weaken): rendering an unseen scene through the new path does no first-use work on the render call (counts); scenes are presented in the order published even when an earlier one's preparation finishes later; a newer scene cancels the wait for an older one that was never shown, but no published Blackout or Clear is ever skipped; the bounded wait switches after the limit; with nothing new, behaviour and the rendered bytes are identical (the existing digest tests `FIXQ_PublishedScenesDigestTests`, `SYS015_ScenesDigestTests`, `UI007c_RenderDigestTests` pass unedited); memory stays bounded (the caches' existing limits hold). New tests in `OUT002c_*.swift`. Do not edit existing tests. No wall-clock assertions: inject the clock and the preparation completion.
4. **Do not run a soak on a real display** (it covers the owner's screen): the coordinator runs it. If an offscreen render of the soak's slide set can show the first-use work is gone (counts), do that and report it.
